# 性能：一支 64 秒极限样片的耗时账

这一篇回答三个问题：**瓶颈到底在哪**、**动了哪几处才下来的**、**凭什么说它已经到极限**。

所有数字都在同一台机器、同一条脚本、同一种口径下测：1920×1080、`scale=1`、
无头 Edge（`--disable-gpu`，也就是**软件光栅化**）、全片 320 个采样点（每 200ms 一个）。

> 为什么故意用没有 GPU 的环境测：这是最坏情况。用户在普通浏览器里打开，WebGL 走显卡，
> 这些数字会低一到两个数量级；而一台没有显卡加速的机器、一个 CI 容器、
> 一个无头浏览器，跑的都是这里量的这条路。**在这个前提下还能跑满 30fps，
> 换到有 GPU 的机器只会更宽裕。**

---

## 一、先有度量，再谈优化

没有度量的优化等于猜。为此在 `src/main.tsx` 的开发调试口上挂了三个只读探针
（`import.meta.env.DEV` 才有，生产包里 `__kly` 是 `undefined`）：

| 口 | 干什么 | 为什么必须是它 |
| --- | --- | --- |
| `frame(ms, scale)` | 渲一帧、返回 PNG dataURL | 出分镜图用 |
| `renderTimed(ms, scale)` | 只渲、不编码，返回毫秒 | `toDataURL` 一张 1080p 要十几毫秒，跟渲染同量级 —— 一起量就把真实开销盖住了 |
| `profile(ms, scale)` | 把一帧拆成「每个图层各花了多少」 | 走的是同一个 `renderScene(onlyLayerId)`，不是另写一条测量路径糊数字 |

方法学上有四条硬规矩，`scripts/perf-check.mjs` 里逐条注释着：

1. **热身再计时**。首次渲染要分配画布、编译 shader、`new Function` —— 量到的是「第一次有多贵」，不是稳态。
2. **复用画布**。一张 1920×1080 的画布背后是 8MB；逐帧 `new` 一张，量到的数字里混着 GC。
3. **取多次最小值**。一次 GC、一次字体回退，会把账算到「正好在渲染的那个图层」头上。
4. **只量渲染**。编码、缩略图、落盘都不算进单帧预算。

前两条不是一开始就有的。最初那版 `profile()` 每条都新建画布，结果**六条音频层
（一个像素都不画）各测出 3.5ms** —— 那不是渲染，那是分配 + GC。这条假数据
差点把优化引到错误的方向上，所以 `src/render/exporters.ts` 现在导出
`renderInto(canvas, …)` 与 `acquireScratch(project, scale)`，让剖析、基准、
逐帧导出共用同一块画布。

## 二、基线：五条判定，通过两条

```
逐层平均耗时（ms / 帧，1920×1080）
   154.85  code    05 · 液态 shader
    41.95  code    06 · 技术账
    28.15  code    03 · 等轴城市
    26.60  code    07 · 风格墙
    19.30  code    01 · 冷开 · 15

全片 320 个采样点
  p50 14.1ms · p95 155.1ms · p99 178.7ms · max 233.2ms
  超 33.3ms 预算：59 点（18.4%）
  FAIL 单帧渲染 p95 在 30fps 预算内（≤33.3ms）    155.1ms
  FAIL 最慢一帧不超过预算的 1.5 倍（≤50ms）       233.2ms
  FAIL 超预算的采样点 ≤1%                        18.4%
结果：2/5 通过
```

一眼就能看出病根：**`p95 = 155.1ms` 和 shader 那一层的 154.85ms 是同一个数**。
整支片子 95% 的时间在等同一层画完，其余八段全是几毫秒的陪跑。

## 三、瓶颈在哪：一条乘法

把 shader 那一层拆开看：1920×1080 ≈ 207 万像素，每像素要算
5 次 fbm × 4 个八度 × 每格 4 个角 = **80 次噪声**。207 万 × 80 ≈ 1.6 亿次，
在 CPU 上跑就是 150ms 上下。

于是这一段的成本可以写成一条乘法：

```
单帧耗时 ≈ 像素数 × 每像素计算量 × 单次计算的单价
```

`单次计算的单价` 是硬件决定的下限，改不动。剩下两个乘数就是全部可操作空间：

- **像素数**：内部分辨率降一半，像素数降到 1/4（平方关系）。
- **每像素计算量**：八度数、噪声次数、能不能提前退出。

canvas2d 那几段也守同一条乘法，只是「每像素计算量」变成了「画了几个盖满全幅的东西」——
`03 · 等轴城市` 一帧里有三次整幅 `fillRect`（底色、地面辉光、地平线辉光），
每一次都是 207 万像素的填充，光这三下就占了它 19ms 里的绝大部分。

## 四、四条优化方向

### 方向一：给代码层加一个内部分辨率旋钮（引擎能力）

`CodeSpec.renderScale?: number`（0.25–1）。渲染时内部分辨率 = 外部倍率
（预览 `zoom × dpr` / 导出 `scale`）× 这一层自己的 `renderScale`，
合成阶段由 `drawImage` 双线性放大回图层尺寸。

两个乘数**故意分开**：一个是「显示多大」，一个是「这一层值不值这么多像素」。

这条是本片最大的一笔，实测（同一个量法：把这一层的 `renderScale` 一档档压下去，量全帧）：

| 内部分辨率 | 实际渲染尺寸 | 全帧 |
| --- | --- | --- |
| 1.00 | 1920×1080 | 66.6ms |
| 0.75 | 1440×810 | 45.2ms |
| 0.60 | 1152×648 | 28.1ms |
| **0.50** | **960×540** | **21.6ms** |
| 0.40 | 768×432 | 13.2ms |

选 0.5 的理由是**够用就停**：这一层是低频的全局噪声场（最高八度也只有 12 个周期 / 画幅），
没有高频细节可丢，半分辨率放大回来肉眼看不出；而 0.5 已经把这一段压到 21.6ms、
离 33.3ms 的线还剩三分之一余量，没必要再往画质那边挪。0.4 更快，但没有理由付那份代价。

**什么该降、什么不该降**写进了字段注释：噪声场、雾、辉光该降；
文字、细线、读数不该降 —— 那些放大后会糊，是真的画质损失。所以整片 9 个代码层里，
只有这一层标了 0.5。

### 方向二：把每像素的噪声次数从 20 降到 13

三级八度，不是通用的 `fbm(octaves)`：

| 用途 | 八度 | 理由 |
| --- | --- | --- |
| `q`（最外层域偏移） | 2 | 只决定「往哪儿扭」，细节会被后面的采样抹掉 |
| `r`（中层折叠） | 3 | 要能把液体拉出丝 |
| `v`（眼睛真正看到的那层） | 4 | 细节全在这里，采样频率也最高 |

八度数变了，和值量级也变（2 八度上限是 0.75 而不是 0.9375），所以 `q`/`r` 各乘一个
常数把明度均值拉回 0.47 —— 否则整幅会暗一档。

少掉的八度会让画面「化开」成大块渐变，所以减八度必须**同时**调大 warp 幅度
（`q` 的系数 2.6 → 3.4，`r` 的 2.2 → 3.1），用折叠量把细节换回来。这一步只能看着画面调。

### 方向三：复用离屏画布，干掉每帧 8MB 的分配

见第一节。导出 WebM 那条路本来就复用一张画布，现在 PNG、逐帧剖析、缩略图、基准
全部走 `renderInto`，不再每帧 `new` 一块 1080p 画布。

### 方向四（走不通，但值得记）：换掉 `sin` 哈希

原本想的是：`fract(sin(dot(p,k)) * 43758.5453)` 每像素要 80 次 `sin()`，
换成无 sin 的整数哈希应该能省一大截。

**实测无效。** 把八度数和分辨率固定住做 A/B，两种哈希的单帧耗时在噪声范围内
（软件光栅化里 `sin` 是多项式展开，和整数哈希只差几个乘加）。
现在代码里留的是整数哈希，理由只是它不依赖 `sin` 的实现精度、跨设备更稳 ——
不是因为它更快。这条记在这里，是为了防止下一次又有人「想当然」地把它当成优化点。

## 五、目标

目标不是「越快越好」，是**在一个写死的画质水位上，把帧预算跑满**。

| 项 | 线 | 依据 |
| --- | --- | --- |
| p95 单帧 | ≤ 33.3ms | 30fps 预算 = 1000/30。工程本身是 30fps，导出也是 |
| 最慢一帧 | ≤ 50ms | 允许一个离群点（首次编译 shader、GC），但不能到 1.5 倍以上 |
| 超预算采样占比 | ≤ 1% | 320 点里最多 3 点。掉帧必须是「偶发」，不能是「每六帧一次」 |

**为什么不定 60fps**：这支片子是 30fps 的，导出也是 30fps。要压到 16.7ms 以内，
内部分辨率得下到 0.35 左右（672×378 放大到 1080p），那是肉眼可见的软 ——
用真实的画质损失去换一个用不到的帧率，不划算。所以 60fps 不做判定，
只在前沿曲线里如实报出来：**在当前画质水位下，60fps 不可行**。

| 指标 | 基线 | 现在 | |
| --- | --- | --- | --- |
| p50 | 14.1ms | **6.4ms** | −55% |
| p95 | 155.1ms | **20.5ms** | −87%（7.6×） |
| p99 | 178.7ms | **22.2ms** | −88% |
| max | 233.2ms | **25.5ms** | −89% |
| 超预算采样 | 59 / 320（18.4%） | **0 / 320** | |
| 判定 | 2/5 | **5/5** | |

而且瓶颈换了人：**shader 不再是第一名**，`03 · 等轴城市`（纯矢量、19.15ms）顶了上来。
这正是「瓶颈被打掉」的证据 —— 它不再是那条 150ms 的长板。

同一台机器连跑几次，p95 在 **18.8–21.8ms** 之间浮动（±8%，来自 GC 与机器负载），
每一次都是 0 点超预算。所以判定线不写成 20ms 这种「刚好压线」的数，
而是留到 33.3ms —— 要证的是「有余量」，不是「这次运气好」。

> 口径说明：基线是同一份脚本测的，但当时 `renderTimed` 每条都新建画布。
> 所以这份对比里有一小部分是度量方式修正带来的（每帧几毫秒），
> 主要部分（150ms → 20ms）是渲染本身变快了。逐层那一列的两端都是 `profile()` 量的，
> 口径一致。

## 七、怎么量化验证「已经到极限」

`node scripts/perf-check.mjs`

一条命令做四件事：逐层剖析 16 个探针点、全片 320 点采样、五条判定、
**画质/耗时前沿曲线**。最后一段是回答「极限在哪」的关键：

```
画质 / 耗时前沿（03 · 等轴城市 @ 22000ms，全帧耗时）
  内部分辨率 1.00  1920×1080    19.6ms
  内部分辨率 0.75  1440×810    13.2ms
  内部分辨率 0.60  1152×648    10.4ms
  内部分辨率 0.50   960×540     8.3ms
  内部分辨率 0.40   768×432     6.9ms
  内部分辨率 0.30   576×324     5.2ms
  60fps（≤16.7ms）可行：内部分辨率 0.75 时 13.2ms
```

这条曲线的作用不是「证明我们够快」，而是**把取舍摊开**：想更清楚就往上走，
想更快就往下走，代价是一行数字。选点逻辑只有一条 —— **取「画质开始肉眼可辨地掉」
之前那一档**。`05 · 液态 shader` 选 0.5、其余层选 1.0，都是这么定的，
而且写进了工程数据（`sample-check.mjs` 有一条断言守着：只有那一层是半分辨率）。

「极限」在这个语境下的定义是：

1. 单帧耗时已经和「像素数 × 每像素工作量」这条乘法贴死，没有可回收的固定开销
   （音频层从 3.5ms 降到 0.0x 就是这条的证据）；
2. 再往前一步必须**降低画质**（曲线左半边），而不是改代码；
3. 换到有 GPU 的机器上，这条乘法整体下移一两个数量级 —— 也就是硬件红利还在，
   软件侧已经压到底了。

## 八、还没做的

- **canvas2d 静态底色预烘焙**。`03 · 等轴城市` 每帧重画三次整幅渐变，而它们其实
  是静止的 —— 烘焙成一张图再 `drawImage` 能再省几毫秒。但代码层沙箱里
  `document` 是 `undefined`，拿不到离屏画布，需要给 `api` 加一个 `scratch(name)`
  的口子。这是 API 变更，得配文档与模板，留到下一次。
- **按图层自动挑分辨率**。现在 `renderScale` 是人写的。真正的自适应要能在未知内容上
  判断「这一层能不能降」，风险是降错了就糊，且会让导出结果逐帧漂移 ——
  对成片来说，可预测比快更重要，所以不做。
- **GPU 路径的实测数字**。本文所有数字都是软件光栅化。要在有显卡的机器上跑同一条脚本
  才能拿到「硬件路径」那一列，这台机器上给不出来，就不编。

## 九、v2.11：第三条杠杆（子帧运动模糊）与第二支片的账

v2.10 的两条杠杆是 `renderScale`（省像素，平方下降）和减少每像素计算量。
v2.11 加了第三条：**`code.motionBlur`（花绘制次数，线性上涨）**。

它和前面两条不是一回事，可以叠着算：

```
这一层的时间 ≈ 像素数 × 每像素计算量 × samples
```

由此得到一条反直觉但很有用的推论：**「5 倍」只在层本身很贵时才可怕。**
实测第二支片的 `07 · 引爆 · 叠层`（1920×1080 的 canvas2d 文字 + 5 子帧、快门 44ms），
在引爆段同一批时刻上关掉模糊，整帧中位从 3.2ms 掉到 2.4ms —— 也就是这一层的 5 遍
只花了 **0.8ms**。因为它本来只画几行字，乘 5 仍然是个小数字。

反过来，给那个半分辨率 GLSL 层开 5 子帧会是灾难：它单帧就要十几毫秒，乘 5 直接出预算。
所以纪律是：**模糊给「便宜但有方向感」的层**（文字、线条、logo 甩入），
**不给「贵且低频」的层**（噪声场、辉光）—— 后者用 `renderScale` 省，不用 `motionBlur` 花。

第二支片（`再改一版`，60 秒、19 层、10 个代码层）的全片实测，口径与第六节完全一致
（`renderTimed(ms, 1)`，每 250ms 一个采样点，240 个点）：

| 指标 | 数值 |
| --- | --- |
| p50 | 2.9ms |
| p95 | 13.1ms |
| max | 27.6ms |
| 超 33.3ms 预算的点 | **0 / 240** |

> v2.11 时这张表是 p50 2.3 / p95 28.5 / max 30.9 / 0 超预算，只有 3ms 余量。
> v2.12 把引爆叠层从「5 子帧 · 全分辨率」改成「4 子帧 · 半分辨率」之后，p95 掉到 13.1ms。

### 一个把自己骗过去的教训：步长会藏住峰值

上面那个「0 个超预算」在 v2.11 时**差点是假的**。当时用的是 1000ms 步长、120 个点，
引爆段只有 6 秒，只采到 6 个点。后来把那段单独按 100ms 加密到 110 个点，才看见
`41450ms` 那一处到了 33.5ms —— **刚好越过预算，而整片扫描从它头上跨过去了**。

现在 `perf` 支持 `--from/--to`，就是为了这件事：

```sh
node scripts/render.mjs perf --project prj_sample_revision --from 40500 --to 43000 --step 50
```

一次测 6 个点看不出噪声，同一段连跑三次才看得出浮动范围（max 33.3 / 26.5 / 27.6ms）。

改后引爆段的实测（110 点 @100ms）：p50 11.3ms · p95 14.7ms · max 19.0ms。
单层剖析（`__kly.profile`，41250ms）是这张表把账对上的地方：

```
整帧          30.5ms
  07 · 引爆        7.9ms   GLSL，内部 960×540
  07 · 引爆 · 叠层   7.7ms   canvas2d，4 子帧，内部 960×540
  HUD             0.9ms
```

**同一支片子里，两种层的正确做法完全相反**：模糊给「便宜但有方向感」的层，
`renderScale` 给「贵且低频」的层。引爆叠层两条都用 —— 它既要方向感，
画的东西又只是几十个矩形，所以降分辨率比加子帧划算得多（4 子帧 × 半分辨率
= 原来 5 子帧全幅的 **1/5** 成本，而飞散标签本来就带辉光，半分辨率丢掉的正是辉光里的高频）。

`--samples auto` 则**不建议整片开**：同样在引爆段，自适应采样的实测是 93.7–105ms/帧
（详见 [离线渲染](12-render.md) §2.4）。自适应省的是**子帧数**，`renderScale`
省的是**每个子帧的像素数**，后者是乘法。

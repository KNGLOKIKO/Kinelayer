# 剪辑：从「会动」到「能剪」

v2.12 之前，Kinelayer 能把一沓图层按时间函数渲染成画面，也能导出 WebM —— 但它不是剪辑器。
缺的是四件最基础的事：**素材从哪一秒开始用**（素材入点）、**在哪一刀切开**（分割）、
**接缝处怎么过渡**（转场）、**导入的音频怎么进片子**（音频资源）。

这一篇先讲调研：GitHub 上那些 AI 视频剪辑项目各自在解什么问题，我们借了谁、拒了谁、为什么。
再讲落地：已经做完的、故意没做的、界面怎么让非专业用户不上手就明白。

---

## 一、调研：六个项目，四种解法

> 界面部分在 v2.14 又对齐了一次剪映（左栏九页签、时间轴工具条顺序、预览区悬浮播放条、
> 深灰 + 高亮蓝配色）。这一篇里的「裁剪手柄 / 拖放 / 片段配色」描述仍然有效，
> 只是配色从紫换成了蓝，页签从 6 个变成 9 个。

★ 数与提交活跃度是 2026-10 调研时的快照，会漂；这里记的是**技术路线**，那个不会漂。

| 项目 | ★ | 许可 | 技术栈 | 它真正在解的问题 |
| --- | --- | --- | --- | --- |
| `OpenCut-app/OpenCut` | 32k | MIT | Next.js 15 + Zustand + Canvas；Rust/WASM + FFmpeg WASM + WebCodecs + WebGL；OPFS 存媒体 | 浏览器里做一个**离线可用**的 CapCut。本地 ONNX 跑抠像与字幕，1080p 一分钟成片约 2.1s |
| `diffusionstudio/core` | 1.2k | MPL-2.0 | TypeScript，Mediabunny + WebCodecs | 把视频合成做成**库**：`Composition → Track → Clip`，声明式 API，框架无关 |
| `diffusionstudio/editor` | 3.4k | MPL-2.0 | 同上，带 UI | 「给 agent 用的编辑器」——把 core 包一层可被程序驱动的界面 |
| `designcombo/react-video-editor` | 1.3k | — | React + Remotion | CapCut / Canva 的克隆，**服务端渲染导出** |
| `mifi/lossless-cut` | 45k | GPL-2.0 | TypeScript + FFmpeg | **无损**剪切与拼接：不解码重编码，只在关键帧边界切 |
| `wyattblue/auto-editor` | — | — | Python CLI | 按静音 / 静止 / 黑场**自动决定切点**，再把时间轴导出给 Premiere / DaVinci / FCP |

另有中文生态的 `UniCut（无界云剪辑）`：浏览器 NLE，多轨、钢笔与魔棒 AI 抠图、LUT、lottie，
单用户免费 —— 功能面最接近「完整剪辑器」，但它是**从零建的 NLE**，不是可复用的引擎。

### 四条路线，各自的天花板

1. **FFmpeg 驱动**（LosslessCut / 半个 OpenCut）：切得准、成本低，代价是「切点必须落在关键帧上」。
   LosslessCut 的 README 自己就把这条写成限制：想精确到帧，就得重编码。
2. **WebCodecs 驱动**（diffusionstudio/core、OpenCut 的导出）：解码交给浏览器硬件解码器，
   性能好、内存省。代价是**确定性变差** —— 同一个文件在核显与独显上解码出来的帧可能差一点点，
   而且 `VideoDecoder` 的 seek 语义要求你自己管 GOP。
3. **Remotion 驱动**（designcombo）：React 组件即帧，服务端 `renderMedia` 出片。
   代价是**必须有一台渲染机**，浏览器里看的是另一套近似渲染。
4. **自建光栅器**（Kinelayer 现在这条）：`renderScene(ctx, project, t)` 是纯函数，
   同一份工程在预览、PNG、WebM、图层窗口里画的是同一帧。

## 二、选型：为什么不换引擎

**结论：不搬任何一个项目当底座，只借它们的时间模型与交互约定。**

理由只有一条，但很硬：**Kinelayer 的文档不是「素材 + 轨道」，是「图层 + 时间函数」。**

在 OpenCut / diffusionstudio 里，一段视频是 `{ file, start, duration, offset }`；
在 Kinelayer 里，一个视频层除了这四项还有 `x / y / width / height / rotation / opacity /
blendMode / animation / bindings / transition`，而且 `x` 可以绑表达式、`opacity` 可以挂关键帧。
把渲染换成 WebCodecs + Mediabunny，等于把这套「图层即时间函数」的模型推翻重写 ——
换来的只是导入素材时的解码速度，而我们的瓶颈不在这里（见 [10-performance.md](10-performance.md)）。

**但有三样东西必须借，否则就是重新发明一遍而且发明得更差：**

| 借来的 | 从哪 | 借的是什么 |
| --- | --- | --- |
| **源内偏移**（`trimIn`） | LosslessCut 的 `--start` / offset 概念 | 「片段从素材的第几毫秒开始」必须是**独立的一个数**，不能靠移动片段位置来表达 |
| **片段条 + 拖边缘** | CapCut / OpenCut 的时间轴 | 非专业用户对「拖两端缩短」零学习成本，对「输入入点出点」有学习成本 |
| **转场只设在后一段** | Canva / CapCut 的默认行为 | 用户不该为了一个叠化去改两个片段 |

**明确拒绝的三样：**

- **关键帧对齐**（LosslessCut）：我们不解码重编码，切点可以在任意毫秒 —— 这条限制对我们不成立，
  照搬只会把「切不准」当成特性写进文档。
- **空的磁道**（Premiere / 剪映的「轨道」）：轨道在我们的模型里**就是图层**。
  引入空磁道等于让用户维护一份和图层树平行的结构，两份东西迟早不一致。
- **自动切点作为主路径**（auto-editor）：静音检测在音乐片 / 无人声片里基本失效，
  把它做成默认行为会让用户第一刀就切错。它更适合做成「建议切点」的辅助功能（见第六节阶段 D）。

## 三、范围：复用与新增

### 复用的（一行没改或只加分支）

| 能力 | 复用点 |
| --- | --- |
| 图层树 / 时间轴骨架 | 片段条本来就画在图层行里，行 = 层，不需要第二套模型 |
| 命令总线 + 撤销栈 | 三条新命令走同一个 `defineCommand`，撤销粒度天然是「一次拖拽 = 一步」 |
| `renderScene()` | 预览 / PNG / WebM / 图层窗口共用一个入口，转场只在这一层实现一次 |
| 音频引擎 | `scheduleRange` 已有「按时间排程 + lookahead + 离线整段渲染」，导入音频只是多一个分支 |
| IndexedDB 资源库 | 图片 / 视频 / 字体之外多一个 `audio` 类别，`AssetMeta.duration` 兼作音频时长 |
| 导出管线 | `exportWebm` 逐帧推帧 + `createAudioCapture` 离线混音，一行没改 |

### 新增的

| 新增 | 位置 | 一句话 |
| --- | --- | --- |
| `src/core/media.ts` | 纯函数 | 剪辑时间语义的唯一实现（片段长度、素材取帧、转场进度） |
| `layer.trim` | 命令 | 改入点 / 出点 / 素材入点 / 速度，拖动时合并成一步 |
| `layer.split` | 命令 | 在播放头切开，右半段 `trimIn` 自动累加，关键帧跟着切 |
| `layer.setTransition` | 命令 | 四种转场（叠化 / 下陷黑场 / 滑入 / 擦除），时长夹到片段一半 |
| 导入音频 | 数据 + 引擎 | `AudioLayer.assetId` + `trimIn`，实时播放与离线混音共用一条排程 |
| 时间轴交互 | UI | 片段拖动、左右裁剪手柄、吸附、转场渐变标记、波形 |
| 检查器「片段」区 | UI | 入点 / 出点 / 素材入点 / 转场，图片视频音频三个面板共用一块 |
| 分割键 | UI | 选中片段按 `S` |

### 故意没做的（及什么时候做）

| 没做 | 为什么现在不做 |
| --- | --- |
| 多视频叠轨（真正的多轨剪辑） | 我们的图层顺序就是 z 序，已经有了；再叠一层「轨道」等于两套 z 序 |
| 变速音频 | `playbackRate` 只给了视频。音频变速要重采样，`AudioBufferSourceNode.playbackRate` 能做，但会让波形与排程对不上，得连波形一起重算 |
| 滤镜链 / 调色 | 现有 `brightness / contrast / saturate / grayscale / blur` 是五个固定参数，够用；滤镜链是另一个量级的需求 |
| 自动字幕 / 自动切片 | 要跑模型（Whisper / VAD）。工程现在是零依赖纯前端，加模型等于换一个产品形态 |
| 时间轴多选批量裁剪 | 命令层支持（`runBatch`），UI 还没做框选；先让单段剪辑稳下来 |

## 四、时间语义：三个数字说清楚

剪辑出 bug，九成出在「同一个时刻有四种说法」。所以这一层被压进 `src/core/media.ts` 一个纯函数文件，
预览、导出、时间轴显示**都调它**，谁都不许自己算。

```
clipEnd(layer)      = outPoint > 0 ? min(outPoint, project.duration) : project.duration
clipLength(layer)   = clipEnd - inPoint

sourceTimeMs(t)     = trimIn + (t - inPoint) × playbackRate      // 素材内时刻
```

### 左边缘要同时动两个数

用户拖动片段左边缘时，直觉是「片段变短了」，但**画面不该跟着滑走**：
把 4.2s–8.4s 的片段左边缘拖到 6.0s，用户期望看到的还是原来 6.0s 那一帧，而不是素材往后跳 1.8 秒。

所以左边缘裁剪要同时改两个数：

```
inPoint += delta
trimIn  += delta × playbackRate
```

`trimIn` 是「素材内偏移」，`inPoint` 是「时间轴上的位置」。两个一起动，画面原地不动，只有长度变了。
这条也解释了为什么分割时右半段的 `trimIn` 必须累加 —— 右半段是从素材中间接上去的。

### 转场只写在一个片段上

时间轴上的片段是**对接**的（前一段 0–4200，后一段 4200–8400），不是叠在一起的。
真正的叠化需要 4200–4800 期间前一段还在出帧、后一段同时淡入。

做法是：转场只存在后一段的 `transition` 上，渲染时给前一段**临时延长出点**
（`outgoingExtension()`），延长的长度正好等于后一段的转场时长。前一段在数据里一个字节都没变。

```
前一段: [inPoint ────────── outPoint]        ← 数据
渲染时: [inPoint ────────── outPoint + ext]  ← 只在这一层延长
后一段:                     [inPoint ──────── outPoint]
                            └─ 转场窗口 ─┘
```

三种转场被拆成三件互不干扰的画布操作：

| 转场 | 新画面 | 旧画面 |
| --- | --- | --- |
| 叠化 `crossfade` | alpha 0→1 | alpha 1→0 |
| 下陷黑场 `dip` | alpha 0→1 | alpha 1→0（中间接近全黑） |
| 滑入 `slide` | 从右滑入 + 位移 | 不动 |
| 擦除 `wipe` | 从左往右裁出来 | 不动 |

`dip` 不额外画一张黑场 —— 那张黑场会盖住上面所有图层（包括用户放在顶上的字幕），那是错的。
「中间变黑」是两段同时半透明叠出来的结果，上面的字幕该亮还是亮。

## 五、界面设计要点

给非专业用户做剪辑器，难的不是功能，是**别让他面对一个专业 NLE**。

**1. 一个改动只有一条路径。** 时间轴上拖、检查器里输数字，都发同一条 `layer.trim`。
不存在「拖了之后数值对不上」这种事，因为数值就是命令的结果。

**2. 片段条上能看见的，就是能改的。** 悬停出两个 6px 宽的手柄（左 / 右），
拖左边缘的 tooltip 直接写「素材不会跟着滑走」—— 这句话比任何文档都省事。
有转场的片段，左边一条渐变标记，悬停显示「转场 叠化 · 600ms」。

**3. 吸附，但只在 8px 以内。** 播放头、其它片段的边、0、结尾。非专业用户对不齐是常态，
但吸得太狠会让人拖不动，所以只吸 8px 内的最近一个目标。

**4. 「片段」排在媒体参数之前。** 图片、视频、音频三个面板共用同一个 `ClipSection`，
放在资源卡、播放速度、音源**上面** ——「这一段在时间轴上的哪一段」是这三类共同的第一属性，
换个图层类型不该换个地方找。画布几何（变换 / 外观）仍在它上面：那是所有图层共有的，不属于剪辑。

**5. 默认值全部合法。** 新建的层 `transition: null` / `trimIn: 0`，一进来就是硬切；
想试转场就选一个，不想试就永远不碰。转场时长夹到片段一半，短的片段上不会整段都在转场。

**6. 说人话。** 不写「入点 / 出点 / 源偏移」，写「入点 / 出点 / 素材入点」；
不写「transition.duration」，写「转场时长」；分割失败不弹错误码，弹「切不开」。

## 七、验证：像素说话

数据模型对不对，看自检输出就够了；**画面对不对，只能取像素**。
`scripts/media-check.mjs` 在真实浏览器里现造一段左红右蓝的 WebM 和一段正弦波 WAV，然后：

| 断言 | 怎么证明 |
| --- | --- |
| 素材入点真的改变了取帧 | 同一时刻导两次 PNG，`trimIn` 0 与 300 的字节数 25834 vs 317422 |
| 分割把 `trimIn` 累加对了 | 500ms 处切开，右半段 `{inPoint: 500, outPoint: 1000, trimIn: 500}` |
| 转场时长被夹到片段一半 | 500ms 片段上设 300ms，实得 250ms |
| **叠化中点同时有红与蓝** | 切点处取像素 `[68, 6, 138]`，前帧纯红 `[255,0,0]`、后帧纯蓝 `[0,0,255]` |
| 导入音频进了离线混音 | 8 秒渲染 peak 0.2636 / rms 0.0569 |
| 波形算得出来 | `peaksFor` 返回非零峰值数组 |

第四条是这一版最该看的：如果转场只做了「新画面淡入」，中点会是纯蓝或偏蓝；
如果做了硬切，中点会是纯红或纯蓝。`[68, 6, 138]` 是红蓝各半，说明**前一段真的还在出帧**，
`outgoingExtension()` 生效了。

## 八、已知限制

- **视频逐帧 seek 有代价**：导出时每帧都要 `currentTime = sourceTime`，长片段导出会明显慢于无剪辑工程。
  缓解办法是只在跨过关键帧时 seek（浏览器自己会做），我们不额外加缓存 —— 缓存会吃掉内存。
- **`trimIn` 只对视频和音频有意义**。图片没有「素材内时间」，所以 `ImageLayer` 上没这个字段；
  给图片层写 `trimIn` 会被 schema 拒掉。
- **转场不嵌套**：一个片段只能有一个入点转场。想出「前一段淡出 + 后一段滑入」需要两次操作，
  现在不支持一次设置两段不同的转场。
- **音频波形是整段算的**，不随 `trimIn` 重算 —— 波形画的是素材的包络，
  裁剪后用 `from` / `to` 参数截取区间显示，所以视觉上和听感一致，但峰值精度是按整段分的桶。

# 12 · 离线渲染：把 pdoom-video 的 Render the Video 逐项搬过来

这一章是一次**逐项对位**。原项目是 [mexicat/pdoom-video](https://github.com/mexicat/pdoom-video)，
它的 README 里有一段 "Render the Video"，讲了七件互不相干的事：输出参数、子帧运动模糊、
双浏览器并行、背压、四种额外模式、真 4K、编码码率。这里逐条说清楚：

- 对应到本工程的**哪个文件、哪几行**；
- **对齐到什么程度**，以及没对齐的那些**为什么**；
- 环境不允许的地方，**上限被顶到了哪里**、还有什么替代方案。

一句话结论先放这儿：

> 七项里 **五项完全对齐**（输出参数、并行分块、背压、四种模式、编码），
> **一项部分对齐**（4K：参数通了，但 CPU 上跑不出可用帧率），
> **一项只能换个实现路径**（瓦片级自适应采样：判据相同，但省不下像素）。
> 另外有三处是**环境限制而不是实现取舍**：没有 ffmpeg、没有 GPU、CPU 光栅化的成本上限。
> 这三处都给了降级路线与安装命令，不假装做到了。

对位总表：

| 原项目 | 本工程 | 对齐度 |
| --- | --- | --- |
| 1920×1080@60 · x264 CRF 16 · AAC | 同参数，帧率跟工程走（本片 30fps） | 完全 |
| `--samples auto` 32×32 瓦片自适应 | `render.mjs --samples auto` + `drawAdaptive()` | 判据同、上限 32（原 324）、不能按块跳过绘制 |
| `--shutter 0.2`（帧时比例） | 同一口径可直接粘，< 1 按比例换算 | 完全 |
| `--workers 2 --chunk 8` → 一个 ffmpeg | 同参数、同结构 | 完全 |
| `--mem-gb 1` / `--spool-gb 20` | `--mem-frames 24`，无磁盘 spool | 内存背压对齐，spool 不需要（原因见 §4） |
| `stills` / `sheet --cuts` / `perf` | 三个都有，`perf` 还多 slice 剖析 | 完全 |
| `plates` | 无此命令名，等价物是 `stills --at` | 完全（它是用法约定，不是能力） |
| `--scale 2` 真 4K | 参数通，CPU 上没有可用帧率 | 部分 |
| `--x264 aq-mode=3:rc-lookahead=30` | `--x264` 直通 | 完全 |

## 1 · 输出参数

**实现要点。** `scripts/render.mjs` 的 `FfmpegSink` 拼出来的 argv 是一条标准的
`image2pipe` 管道：

```
ffmpeg -y -f image2pipe -framerate <fps> -i - [-i audio.wav]
       -c:v libx264 -crf <crf> -preset <preset> -pix_fmt yuv420p
       [-x264-params <--x264>] [-c:a aac -b:a 192k -shortest] <out>
```

默认 `--crf 16`、`--preset medium`、`yuv420p`（不是 `yuv444p` —— 上传播放器只吃 420），
音频 192k AAC。这三样与原项目逐字一致。

**对齐程度：完全。** 唯一的差别是帧率跟工程走（本片 30fps），可以用 `--fps 60` 覆盖。
`--fps` 只改**输出时间轴**，不改工程：每帧的渲染时刻仍然是 `from + i * (1000/fps)`，
所以同一毫秒渲出来的永远是同一张图，换帧率只是换采样密度。

**限制点。** 没有 ffmpeg 时 `video` 模式自动降级成 `sequence`（PNG 序列 + 一条可粘的
`encode.cmd` / `encode.sh`）。这是本机的实际情况：`ffmpeg -version` 返回 command not found，
`where.exe` 空，`Program Files/ffmpeg`、scoop shims、WinGet Links 都没有。

```bat
winget install Gyan.FFmpeg
:: 或
scoop install ffmpeg
```

装完不需要改任何代码 —— `hasFfmpeg` 是每次启动时 `spawnSync` 探的。

**为什么不自己写编码器。** 无压缩 AVI 一帧 6MB，60 秒 1080p 是 11GB；
自己实现 x264 的替代品（哪怕是 MJPEG）要做的取舍比调一次 `-crf` 多得多。
PNG 序列这条路的好处是**帧是完整的**：编码器换了、参数错了，重编一次就行，不用重渲。

## 2 · 子帧运动模糊与自适应采样

这是七项里最长的一项，也是唯一一项**不能完全照抄**的。

### 2.1 原项目的做法

- 一帧 = 多个子帧的平均，子帧铺在 `shutter` 这段曝光里（`--shutter 0.2` = 一帧的 1/5）；
- `--samples auto` 按 **32×32 瓦片**给每块挑子帧数：静止 12、普通镜头运动 36、甩镜 108 或 324；
- 一块「再多的子帧也不会让它变化超过 `--tol` 个色阶（默认 3）」就停，**后续子帧跳过它**；
- `--refine frame` 改成整帧一个计数（更慢，是瓦片采样器之前的老做法）。

### 2.2 本工程的做法

`src/render/codeEngine.ts` 的 `drawAdaptive()`，逐级加密：

```
stage 4  → 画 0,8,16,24   → 量一次收敛
stage 8  → 补 4,12,20,28  → 量一次
stage 16 → 补偶数位       → 量一次
stage 32 → 补奇数位       → 量一次
```

三个关键决定，都写在代码注释里：

1. **子帧位置固定在 `i/(AUTO_MAX-1)` 格点上，逐级加密（stride 4→2→1）。**
   补样本永远是往空隙里塞，已经画过的那些不会因为总数变了而挪位置 ——
   累积平均才是无偏的。原项目每次 refine 会重铺位置，那在 GPU 上无所谓（重画很便宜），
   在这里等于把已经付过的钱再付一遍。
2. **上限 32，不是 324。** 见 §2.4 的算术。
3. **不能按瓦片跳过绘制**，所以瓦片只用来判断「还要不要继续」。

```ts
const AUTO_MAX = 32;
const AUTO_STAGES = [4, 8, 16, 32];
```

### 2.3 一个必须说清楚的真相：瓦片判据 ≡ 整帧判据

`maxTileDelta()` 对每个 32×32 块内取 |Δ| 最大值，再**对全图取最大**。
对全图取最大，等于整帧取最大 —— 瓦片结构从来没有影响过决策。

这是实测发现的，不是推理：

| 判据 | 41200–41800ms 的耗时 |
| --- | --- |
| 逐 32×32 块取最大 | 约 100ms |
| 整帧取最大 | 约 100ms |
| 逐块取最大 + `tol 8` | 约 105ms |

三条一模一样。所以我一度加过一个 `--refine tile|frame` 开关，测完**删掉了**：
一个什么都不改变的开关比没有开关更坏 —— 用户会以为自己在调优。

**为什么瓦片语义在这里复刻不了。** 原项目靠 scissor 让收敛的瓦片不再跑着色器，
于是「一块静了」真的省下一次着色。canvas2d 没有 scissor 等价物
（`clip` 反而更贵，它要建一条路径再求交），一次子帧必须整帧重画。
所以：

- 杠杆①「静止瓦片不再绘制」→ **不可复刻**，省不下像素；
- 杠杆②「瓦片各自计数」→ 退化成**全帧统一计数**，也就是原项目的 `--refine frame`。

本工程的 `--samples auto` 因此在语义上**等价于原项目的 `--refine frame`**，
而不是它的瓦片采样器。这句话写在 `maxTileDelta` 的注释里，不藏在文档里。

### 2.4 上限 32 的算术

原项目 324 次子帧在 GPU 上跑得动：一次全屏绘制是几毫秒的**着色**，324 次也就一秒级，
而且它只对需要的那部分像素着色。这里是 CPU 光栅化 —— 1080p 一层一次绘制 1~3ms，
324 次就是一帧 300ms 以上。**上限 32 是这么来的，不是拍脑袋：**

```
1080p 一层一次绘制            1.5 ~ 3ms
× 32 子帧                    48 ~ 96ms      ← 已经超 33.3ms 预算
+ 3 次 getImageData + 扫描    ~10ms
```

实测印证了这个估算：在引爆段（`07 · 引爆 · 叠层`，1080p 全幅、几十个飞散标签），
`--samples auto` 的实测是 **100–105ms/帧**，5/6 的采样点超预算。引爆段的三种配置：

| 配置（引爆段同一批时刻） | p50 | p95 | max | 超预算 |
| --- | --- | --- | --- | --- |
| 固定 5 子帧 · 1080p 全幅（v2.11） | 3.1ms | 43.0ms | 48.1ms | 3 / 120 |
| `auto` · 全幅 · tol 3 | 93.7ms | 100.0ms | 100.0ms | 5 / 6 |
| 固定 4 子帧 · `renderScale 0.5`（v2.12） | 11.3ms | 14.7ms | 19.0ms | 0 / 110 |

结论：**`--samples auto` 在本工程是「能用但很贵」**，给一两层用可以，
整片开等于把 30fps 的片子渲成 10fps。默认路线是「固定少数子帧 + 降内部分辨率」，
两条杠杆叠起来比自适应更划算 —— 因为自适应省的是**子帧数**，
而 `renderScale` 省的是**每一个子帧的像素数**，后者是乘法的。

### 2.5 `--shutter` 的口径：让原项目的命令能原样粘

原项目写 `--shutter 0.2`，单位是**帧时比例**。本工程存的是毫秒（图层不知道自己挂在
什么帧率上，比例对它没有意义）。为了兼容，`render.mjs` 里做了一次显式换算：

```js
if (v < 1) return v * (1000 / fps);   // 0.2 @30fps = 6.67ms
return v;                             // ≥ 1 就是毫秒
```

这个歧义是安全的：0.2ms 的快门在任何帧率下都没有意义（比一次绘制还短），
所以「< 1 就是比例」不会误伤任何真实用法。运行时会打一行日志确认换算结果。

但**本片没有用 0.2**。30fps 下一帧 33.3ms，0.2 帧时 = 6.67ms，
配 4 个子帧等于 4 张几乎一样的图 —— 看不出模糊。所以落版用 `shutter: 44ms`
（约 1.32 帧），这是**刻意偏离**：原片是 60fps 下的快镜头加真正的甩镜，
本片的运动物是几十个飞散标签，在 30fps 下每帧位移大得多，快门必须更宽才能连成一条。

> 顺带一个真踩过的坑：**快门是「一帧曝光」，不是「重影次数」**。
> 最早给 110ms（三帧多），得到的是三次离散的重影 —— 那是长曝光，不是运动模糊。

## 3 · 双浏览器并行分块

**实现要点。** `renderFrames()` 把帧切成 `--chunk 8` 一块的队列，
`--workers 2` 开两台无头浏览器，各自领块、各自渲，**全部写进同一个 sink**：

```js
const pages = await Promise.all(Array.from({ length: Math.min(workers, chunkCount) }, (_, i) => openWorker(`worker-${i}`)));
```

有序性由 `createOrderedSink()` 保证：谁先渲完无所谓，写出去必须按帧号。
所以「两个渲染器乱序产出、一个编码器按序吃进」得到的文件与单渲染器**逐字节同构**
（x264 是确定性的，同样的帧序列得到同样的码流）。

**对齐程度：完全。** 参数名都一样（`--workers` / `--chunk`）。

**为什么两个就够。** 原项目的解释是「一个渲染器已经把 GPU 占满，第二个填轻场景的空档」。
本工程的理由不同但结论一样：CPU 渲一个 1080p 帧要 3–30ms，Node 侧 PNG 解码 + 写盘
是另一个核上的活，两块流水刚好把两件事叠起来。`--workers` 上限是 4，但本机只有 8 核
（还要留两个给 dev server 和 Node 那侧），再往上加是四个浏览器抢同一批核。
这个上限**没有实测到拐点**，所以只把它当「别开太多」的保守值，不当结论。

**实测吞吐**（整片 1800 帧，2 个渲染进程，每块 8 帧）：

| 口径 | 数值 |
| --- | --- |
| 整片 60 秒 / 1800 帧 | **89.0 秒 · 20.22 帧/秒** |
| 引爆段 10 秒 / 300 帧（最贵） | 26.4 秒 · 11.38 帧/秒 |
| 产物（PNG 序列） | 1800 帧 / 353MB |
| 音轨（WAV 48k/16bit 立体声） | 11.5MB |

也就是说 60 秒成片的离线渲染时间是 **1.5 倍实时**。原项目那支片约 57 分钟（4K，GPU），
换算到 1080p 大概也是几倍实时 —— 数量级一致，但原因完全不同：它是 GPU 被 324 子帧压满，
这里是 CPU 光栅化。

**一个真挂住过的 bug，值得整段记下来。** 整片渲染在 `--samples auto` 之后一度
**卡在第 1350 帧（45000ms，引爆段结尾）不动，卡了 19 分钟**，没有异常、没有退出码，
表现和「机器慢」一模一样。三层原因叠在一起：

1. **背压规则会死锁。** 原来是「待写帧超过 `--mem-frames` 就等」，而两个渲染进程
   同时跑到写出口前面很远时，待写的全是出口之前的帧；真正该写的那一帧还没渲完，
   两个进程就一起睡在等待里 —— 谁也不再产帧，出口永远不动。
   现在的规则是「每个进程只保证自己比我该写的那一帧超前不超过 `--mem-frames`」：
   拥有出口那一帧的进程永远不被拦，只要它在跑出口就会动，**构造上不可能死锁**。
2. **CDP 调用没有超时、也不听断连。** 页面崩了以后 `await` 一个永远不会来的回复。
   现在 `Runtime.evaluate` 有超时（`--frame-timeout`，默认 90s），WebSocket 一关
   立刻把所有在等的调用 reject。单帧失败会**换一台浏览器重渲这一帧**（最多 2 次），
   因为每帧是时间的纯函数，换机器渲出来的应该是同一张图。
3. **非 TTY 没有心跳。** 日志被 `| tail` 吞掉的时候，「挂了」和「在跑」看起来完全一样。
   现在每 60 帧落一行完整的进度，另有一个停滞看门狗：出口 90 秒没动就打印
   「卡在哪一帧、待写帧的索引范围」然后退出 —— 任何未来的死锁都会以报错结束，
   而不是以「跑了 20 分钟没结果」结束。

> 教训：**一个静默挂住的渲染器比一个报错的渲染器坏得多。** 报错你知道要重跑，
> 静默挂住你会先去怀疑机器。

**一个真出过的 bug，值得记下来。** `openWorker()` 早期只等 `!!window.__kly` 就算就绪。
`Page.navigate` 是异步的，旧页面上的 `__kly` 还活着，于是 `meta()` 读到的是**上一个工程**。
症状是「渲染成功了，但渲的是别的东西」（示例海报 · 1080×1440 · 4s，而不是要的那支 60 秒片），
比直接报错难查得多。现在等的条件是：

```js
window.__kly.state().project.id === PROJECT
```

## 4 · 背压：内存排队，但不落盘

**实现要点。** `createOrderedSink()` 里有一个 `pending: Map<index, Buffer>`，超过
`--mem-frames`（默认 24）就让渲染端 `await` 一下，等编码器追上来。

**对齐程度：内存这一半对齐，磁盘 spool 没有 —— 而且不需要。** 理由是**背压方向相反**：

| | 原项目 | 本工程 |
| --- | --- | --- |
| 瓶颈 | GPU 渲得快，x264 跟不上（4K 下 CRF 16 是 670 Mbit/s） | CPU 渲得慢，x264 永远吃不饱 |
| 后果 | 帧在内存里堆积 → 必须落盘 spool 才能不阻塞渲染 | 不会堆积 → spool 永远不会被写满 |
| 需要的机制 | `--mem-gb` + `--spool-gb` 两级 | 一级就够 |

换句话说，spool 在原项目里是**性能设施**（让渲染器别等编码器），
在这里是**永远不会触发的死代码**。为一个 60 秒的片子写一套 GB 级落盘队列，
换来的是「一个从来不会执行的路径」，这不叫对齐，叫复杂度。

**单位为什么是帧数而不是 GB。** 每一帧交出去的时候就是一个 PNG Buffer，
`buf.length` 是精确已知的，所以「排 24 帧」的内存上界是可算的（实测 1080p 一帧
约 0.3–1.2MB，24 帧不到 30MB）。用 GB 反而要额外做一次水位估算。

**如果真要落盘**（比如 4K 长片，一帧 8MB，24 帧 192MB），改动点只有一处：
`createOrderedSink` 的 `pending` 从 `Map<number, Buffer>` 换成
`Map<number, string>`（临时文件路径），写的时候 `fs.writeFileSync` 到一个按帧号命名的 tmp 目录，
读的时候读完就删。接口不变。

## 5 · 四种额外模式

原项目有 `stills` / `sheet` / `perf` / `plates`。前三个直接对位，第四个是用法约定。

### `stills` — 指定时刻出静帧

```sh
node scripts/render.mjs stills --project prj_sample_revision --at 0,4000,22500
```

`--at` 收逗号分隔的毫秒，也收 `--n 8`（均匀切 8 张）。每张是完整分辨率的 PNG。

### `sheet` — 联络图（contact sheet）

```sh
node scripts/render.mjs sheet --project prj_sample_revision --cuts --cols 4
```

`--cuts` 是原项目的语义：**每个场景边界一格**。本工程直接从 `SECTION_SPANS` 取切点，
不用另外维护一份。拼图在页面里做（`__kly.sheet()`），不是在 Node 里拼 ——
省一次全尺寸位图跨进程搬运。

这一条在本片上是**真的有用的**：13 格联络图一眼能看出第 2 格（3750ms，冷开转第一句）
是奶白一片 —— 那是 `02 · 第一句` 背景柱的起始，不是 bug，
但它确实说明这支片子在切点处有半帧过曝。

### `perf` — 逐帧耗时

```sh
node scripts/render.mjs perf --project prj_sample_revision --step 250
node scripts/render.mjs perf --project prj_sample_revision --from 40500 --to 43000 --step 50
```

输出 p50 / p95 / max / 超预算个数，`--json` 落盘原始样本。**`--from/--to` 对 perf 也生效** ——
这条是补上的：整片按固定步长扫时，越贵的那几段越容易被步长跳过去。
引爆段只有 6 秒，1000ms 一步只采到 6 个点，峰值刚好落在两点之间就是假绿灯
（第一次测出「0 个超预算」就是这么骗到自己的）。

比原项目多一样：`__kly.profile(ms)` 把某一毫秒拆到**每个图层各花了多少毫秒**。
引爆峰值处的实测：

```
41250ms 整帧 30.5ms
    7.9ms  07 · 引爆            (GLSL，内部 960×540)
    7.7ms  07 · 引爆 · 叠层      (canvas2d，4 子帧，内部 960×540)
    0.9ms  HUD · 时码 / 段落 / 逐字歌词
    0.0ms  音频 ×3
```

这张表是「哪一层贵」唯一的客观来源。没有它，调 `renderScale` 只能靠猜。

### `plates` — 本工程没有这个命令名

原项目的 `plates` 是「重出 `public/plates/` 下那批静帧，outro 的倒带蒙太奇要用」。
它不是一个独立能力，是 **`stills` + 一个固定的输出目录 + 一组固定的时刻**。

本片的落版没有倒带蒙太奇，所以没有对位物。但等价物是现成的：

```sh
node scripts/render.mjs stills --project prj_sample_revision --at 3750,10000,22500 --out public/plates
```

如果以后要加倒带蒙太奇，这就是 `plates`，不需要新命令。

## 6 · 4K

**实现要点。** `--scale 2` 把 `renderInto(canvas, project, { scale })` 的每一层
都按物理分辨率渲 —— 不是渲完放大。本工程里 `renderScale` 是**再乘一次**的：

```js
resize(rt, layer, scale * (layer.code.renderScale ?? 1));
```

所以 4K 下 `renderScale 0.5` 的层内部是 1920×1080，与 1080p 渲染时的内部尺寸相同，
只是最终合成到 3840×2160 上。这正是原项目说的「场景按 1920×1080 逻辑像素排版，
4K 帧看起来就是 1080p 的那张，只是更锐」。

`--scale` 对每个模式都生效：`stills` 存 4K PNG，`perf` 量 4K 每帧耗时，
浏览器预览加 `&scale=2`。

**对齐程度：部分。** 参数通了，画面对了，但**没有可用的帧率**。

**限制点及原因。** 原项目 4K 是 GPU 限：一帧 40ms（静帧）到几秒（光线步进的房间 + 324 子帧），
整首约 57 分钟（M5 Pro），内存峰值 23GB。这里是 CPU 限，而且差一个数量级：

```
1080p 一帧                     3 ~ 30ms
4K = 4 倍像素                 12 ~ 120ms   ← 30fps 预算 33.3ms，几乎全线超
```

更麻烦的是**没有 GPU 可借**。CDP 启动参数里带 `--disable-gpu`，所以 WebGL 走 SwiftShader
（软件光栅化）—— 这也是为什么本片那个 GLSL 引爆层在 960×540 下就要 7.9ms。
用户真机有 GPU 时这个数字会小得多，但**离线渲染刻意不开 GPU**：
软光栅的像素是确定的，跨机器一致；GPU 的 AA、着色器精度、色彩管理都跟驱动走，
同一份工程在两台机器上会渲出不同的文件。这条「确定性」比速度重要。

**增强方案（顶上限的三条，按性价比排序）**：

1. **`--scale 1.5`**（2880×1620）。像素量是 4K 的 56%，多数播放场景看不出差别。
   这条现在就能用，不需要改代码。
2. **降到 24fps 渲 4K**。`--fps 24` + `--scale 2`，预算从 33.3ms 放宽到 41.7ms。
3. **分段并发**：把片子切成 N 段，每段一个 `render.mjs` 进程 + 自己的浏览器对，
   最后 `ffmpeg -f concat` 拼。本机 8 核，理论上 2 段能拿到接近 2 倍。
   代价是每段要各自付一次启动与音频渲染的成本，且要注意接缝处的帧号对齐。

## 7 · 编码与码率

原项目给了一组很有用的 4K 实测：颗粒（grain）是逐 4K 像素渲的，极难压，
CRF 16 ≈ 670 Mbit/s（整首 13GB，是 1080p 的 8 倍）、CRF 18 ≈ 450、CRF 20 ≈ 230。
`--x264 aq-mode=3:rc-lookahead=30` 是用来压内存的（让 x264 少缓存前瞻帧）。

**对齐程度：参数完全对齐。** `--x264` 是直通：

```sh
node scripts/render.mjs video --project prj_sample_revision --scale 2 --x264 aq-mode=3:rc-lookahead=30
```

**限制点。** 这组数字在本工程**无法验证**：本机没有 ffmpeg，也没有 4K 的 GPU 渲染能力。
所以 §7 在这里只能抄参数，不能抄结论 —— 这是文档里唯一一处「引用别人的实测」，
需要标明出处，不能当成自己的数据。

顺带一个差异：本工程的画面**没有逐像素颗粒**。颗粒是原项目码率的主因
（`src/engine/` 的后处理里有 grain/halation 两个 pass），本工程的后处理只有辉光与噪声场，
而且噪声场的 `renderScale` 通常不是 1。所以同等 CRF 下本工程的码率会显著低于 670 Mbit/s，
这既是好事（文件小），也意味着**那组数字不能直接套过来做容量预估**。

## 8 · 环境限制清单

三条，都不打算假装绕过。

| 限制 | 表现 | 原因 | 替代 / 修法 |
| --- | --- | --- | --- |
| 没有 ffmpeg | `video` 降级成 `sequence` + `encode.cmd` | 本机 PATH 里没有，`winget`/`scoop` 都没装过 | `winget install Gyan.FFmpeg` |
| 没有 GPU | WebGL 走 SwiftShader，GLSL 层贵 5–10 倍 | CDP 启动带 `--disable-gpu`，且这是**故意的**：软光栅保证跨机器像素一致 | 预览用真机 GPU 看效果，离线仍用软光栅出片 |
| CPU 光栅化上限 | 子帧上限 32（原 324）；无 scissor，瓦片省不下绘制 | canvas2d 没有 scissor 等价物；1080p 一次绘制 1~3ms | 用 `renderScale` 降像素而不是加子帧（§2.4） |

还有一条不是「限制」但会影响判断：**所有耗数字都是在没有 GPU 的机器上量的**。
它高估了 GLSL 层的成本，但没有高估 canvas2d 的成本 —— canvas2d 本来就是 CPU 光栅化，
软硬件的差别只在这一层上。

## 9 · 本工程多出来的东西

对位不是只有减法。这几样原项目没有：

1. **`perf` 的图层切片**（`__kly.profile`）。原项目的 `perf` 只报整帧。
   拆层是调优的前提，没有它就不知道该降哪一层的 `renderScale`。
2. **`perf --from/--to`**。缩小范围加密采样，专门对付「峰值落在两个采样点之间」。
3. **WAV 而不是 WebM 音轨。** 外部编码器读不了 `MediaRecorder` 封装的 WebM，
   `renderWav` 用 `OfflineAudioContext` 渲 48kHz / 16bit / 交错 PCM，交给 ffmpeg 的第二路输入。
4. **PNG 而不是原始 RGBA。** 1080p 一帧 RGBA 是 7.9MB，base64 之后 11MB，
   跨 CDP 传一遍纯属浪费；PNG 在页面里编码（每帧十几毫秒），实测压缩比 **13 倍**
   （本片平均 623KB/帧，最复杂的爆炸帧 1.4MB），传输量降到原来的 1/13。
5. **`encode.cmd` 与 `encode.sh` 双份**。降级路线上手的人可能在任何 shell 里。

## 10 · 自检

`scripts/render-check.mjs`（`npm run render:check`）把四个模式各跑一遍，断言的是**形状**而不是像素：

```sh
node scripts/render-check.mjs
```

```
  ✓ stills  3 张 · 平均 71KB
  ✓ sheet  3 格 · 44KB
  ✓ sequence  9 帧
  ✓ audio.wav  11.0MB · RIFF/WAVE · 编码脚本就位
  ✓ perf  3 点 · p50 10.9ms · max 16.5ms
```

五条断言各自防一类故障，都不是「画面好不好看」：

| 断言 | 防的是 |
| --- | --- |
| `stills` 出图数量 + 三张不全相同 | 时刻参数没生效（三张都是第 0 帧） |
| `stills` 每张 > 20KB | 画布是空的（纯色 1080p PNG 只有几 KB） |
| `sheet` 格数 = `--at` 给的时刻数 | 拼图漏格或多格 |
| `sequence` 帧数 = `(to-from)/1000×fps` | 少帧 —— 这种错成片能播，只是偷偷短了一点 |
| `audio.wav` 是 RIFF/WAVE + `encode` 脚本在 | 无声片，或者没 ffmpeg 的机器上无路可走 |

像素级的正确性由「同毫秒必同帧」这条不变量保证，那件事在 e2e 里验（预览、导出、图层窗口
走的是同一个渲染函数），不在这里重复。跑一次约 20 秒，需要 dev server 起着。

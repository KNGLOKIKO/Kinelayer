# 16 · 可借鉴清单：Adobe 三件套与 PhotoCraft

> 这份文档的作用是**剔除**，不是许愿。
> 三个产品的能力加起来上千项，Kinelayer 能吸收的不到二十项；剩下的不是不够好，是文档模型不同构 ——
> 硬搬会把「参数化时间轴」改成「半个 Photoshop」，那是换一个产品，不是加功能。
>
> 调研边界：Adobe 三件套只依据公开文档、官方功能说明与已公开的格式规范（本机也只装了 Creative Cloud
> 客户端，没有应用本体可分析）；PhotoCraft 是 MIT / Apache-2.0 开源，直接读其仓库 README 与 `docs/`。
> **没有反编译任何 Adobe 二进制，也没有抄任何代码**，取的是设计模式。

## 一、先摆清坐标系

| 产品 | 文档是什么 | 一次修改的单位 | 「非破坏性」靠什么 | 交付形态 |
|---|---|---|---|---|
| Photoshop | 像素矩阵 + 图层栈 | 一笔 / 一次滤镜（改像素） | 调整层、智能对象、图层蒙版 | 位图（PSD / PNG / TIFF） |
| Lightroom | 一张原图 + 一组参数 | 一个滑杆（改参数） | 参数即编辑，从不写回原图 | 导出派生文件 |
| Illustrator | 矢量对象树 + 画板 | 一个锚点 / 一次外观属性 | 外观面板、符号、全局色 | 矢量（AI / SVG / PDF） |
| PhotoCraft | 像素 + 图层 + 调整层（PS 同构） | 一条命令 | 同 PS，且瓦片级撤销 | 位图 + PSD |
| **Kinelayer** | **图层数组 + 时间函数** | **一条 Command** | **文档本来就是参数** | **帧（PNG）/ 视频（WebM）/ 字幕 / 剪辑表** |

结论三条，后面所有判断都由它们推出来：

1. **Kinelayer 天生属于 Lightroom 那一类**（参数即文档），而不是 Photoshop 那一类（像素即文档）。
   所以 Lightroom 的模式适配度最高，几乎不用改造就能借。
2. **Photoshop 的「编辑像素」类能力，移植时必须翻译成「变换参数」。** 翻译得动的（调整层、图层样式）
   能要；翻译不动的（画笔、选区、钢笔）要不了。
3. **Illustrator 的价值不在绘图，在「一份设计多种输出」的组织方式**（画板、全局色、符号）。
   这三样恰好都是参数化的，适配度也很高。

## 二、逐维度评估

### 2.1 图像编辑

**对方怎么做（实现模式）**

- Photoshop 的非破坏性靠三层结构：**调整层**（16 种，作用于其下所有层，可剪贴到单层）、
  **图层蒙版**（灰度图决定透明度）、**智能对象**（内嵌源文件 + 智能滤镜，滤镜参数保留可改）。
- 滤镜是「预览 → 应用」两段：对话框在选区范围内实时预览，确认才落像素；作用于智能对象则转为
  可再编辑的智能滤镜。PhotoCraft 把这套照搬，并做到 70+ 种滤镜全部实时预览。
- 画笔引擎是另一条独立线：笔尖形状 + 动态（Shape Dynamics / Scattering / Texture / Color Dynamics）
  + 压力/倾斜/旋转输入。PhotoCraft 直接读 PS 的画笔预设（`.abr`）。

**本工程现状**

图层只有 6 种（`background` / `text` / `image` / `video` / `code` / `audio`），扁平数组，
**没有组、没有蒙版、没有调整层**。图像层的调色是 5 个 CSS `filter` 参数
（brightness / contrast / saturate / grayscale / blur），**只对 image 层有效**，text 与 code 层拿不到。
合成是「逐层直接画到主画布 + `globalCompositeOperation`」，**没有离屏组缓冲**。

**评估**

| 能力 | 出处 | 实现模式 | 本工程现状 | 判定 | 成本 | 价值 |
|---|---|---|---|---|---|---|
| 调整层（作用于下方合成结果） | PS / PhotoCraft | 组缓冲 + 像素变换 | 无 | 调整后借鉴 | L | 高 |
| 图层样式（投影 / 描边 / 外发光） | PS | 离屏 + composite 叠层 | 文本已有 stroke / shadow | 部分已有，补 2 项 | M | 中 |
| 形状遮罩 / 裁剪进形状 | PS | 蒙版位图或 clip path | 只有圆角 | 调整后借鉴（限几何遮罩） | M | 中 |
| 智能对象（内嵌源 + 可改滤镜） | PS / PhotoCraft | 内嵌文件 + 参数化滤镜链 | `remotion-component` 层已是同构物 | 调整后借鉴（推广为嵌套工程） | L | 中高 |
| 画笔 / 选区 / 钢笔 / 滤镜库 | PS | 像素笔触 + 选区位图 | 无 | **不适用** | — | — |

关键判断：**调整层不能照 PS 的语义直接做。** PS 里「作用其下所有层」是自由像素画布的产物；
Kinelayer 的层序是 z 序数组，一个「作用于下方所有层」的调整层会让每次局部重绘都要回溯整条链，
且与 `onlyLayerId`（图层窗口只画单层）、`overrides`（拖拽预览）冲突。
正确的落点是引入**组**，让调整层只作用于组内 —— 渲染时组内合成到离屏 canvas 再变换。
**组不是为了整理，是调整层的作用域。**

这也意味着：**组和调整层必须同一批做。** 单独做组（纯组织功能）投入产出比很差，
它能省的只是批量显隐，而用户真正要的是「这一整块一起调色、一起动」。

### 2.2 色彩管理

**对方怎么做**

- Photoshop / PhotoCraft：ICC 全链路。文档带色彩模式（RGB / CMYK / Lab / 灰度）与位深（8 / 16 / 32），
  **Assign 与 Convert to Profile 分开**（前者改解释、后者换算像素），四种渲染意图 + 黑点补偿，
  软打样（⌘Y）与色域警告在 GPU 上做。PhotoCraft 用纯 Rust 实现；纯前端等价物只能是 lcms 的 wasm 构建。
- Lightroom：不暴露 profile 细节，给的是「相机配置文件 + 白平衡 + 色调曲线 + HSL（按色相区间）+
  分离色调 + 颜色分级」。真正值得抄的不是滑杆，是**管线顺序固定**：输入 profile → 白平衡 → 曝光 →
  对比 → 高光/阴影 → 曲线 → HSL → 分级 → 输出 profile。

**本工程现状**

canvas2d，sRGB，8bit。颜色全是 CSS 字符串，散落在每层字段里（`color`、`gradient.stops`、
`stroke.color`、`shadow.color`）。没有任何 profile 概念，导出 PNG / WebM 都是 sRGB。

**评估**

| 能力 | 出处 | 实现模式 | 本工程现状 | 判定 | 成本 | 价值 |
|---|---|---|---|---|---|---|
| ICC / CMYK / 16bit / 软打样 | PS / PhotoCraft | 色彩引擎 + 模式转换 | 无 | **不适用**（见下） | XL | 低 |
| 参数化调色管线（曝光/对比/曲线/HSL） | Lr | 固定顺序的纯函数链 | 仅 image 层 5 个 filter | 调整后借鉴 | M | 高 |
| 全局色 / 色板（改一处全改） | Ai（Global Swatch） | 颜色槽 + 引用解析 | 无 | **直接移植** | S-M | 高 |
| 色域 / 安全区检查 | PS Gamut Warning | 越界像素高亮 | 无 | 降级借鉴（改为安全区） | S | 中 |

**为什么 ICC 不做**（这条要写死，免得以后反复提）：

1. canvas2d 的像素格式就是 8bit sRGB，16bit 通道与 CMYK 无处落脚；
2. WebM 编码出来是 8bit YUV，在编码前做色彩管理是自欺；
3. 全链路色彩管理要求**每一个合成步骤**都在目标空间里做，而本工程的合成一半在 canvas2d、
   一半在用户代码层（`runCodeLayer` 里是任意绘制），无法约束；
4. 真要印刷交付，正确做法不是内建 CMYK，而是**导出时嵌入指定 ICC profile**（PNG 的 `iCCP` chunk），
   让下游去转换。这是「交付」问题，不是「编辑」问题。

**调色管线要借，但要借对。** Lightroom 的顺序固定比它有哪些滑杆更重要：允许任意排列调色步骤，
预览与导出就会因为浮点累积顺序不同而出现肉眼可见的偏差。建议做成**固定顺序的单一 `colorGrade`**
（作用于整帧或组的结构体），而不是「任意堆叠的调整层」—— 小成本换大确定性。

同时要认清 canvas2d 的能力边界：`ctx.filter` 能表达 brightness / contrast / saturate / hue-rotate /
sepia / blur / invert；**表达不了曲线、色阶、HSL 分区间、分离色调**。后者要么 `getImageData` 逐像素
（1920×1080 单帧约 8–15ms，30fps 边缘），要么 WebGL。所以第一版**只做 filter 能表达的子集**，
一致性天然成立；「只在导出时高精度」会制造预览/导出偏差，那是本工程明确不能碰的底线。

**全局色板是被低估的一条。** 海报模板的真实工作流是「这套配色换成客户 B 的」，现在是逐层改 20 处。
改成 `Project.palette`（命名颜色槽）+ 图层颜色允许引用槽位，解析放在渲染前的纯函数里，一次替换即可。
额外收益：**AI 生成模板时只需产出 palette + 结构，颜色由人指定** —— 比让模型逐层写十六进制色值可靠得多。

### 2.3 图层处理

**对方怎么做**

- PS：组（可嵌套，自带 blend / opacity / mask）、剪贴蒙版（上层只作用于下层的不透明区）、
  **图层复合**（Layer Comps：把可见性/位置/外观的组合存成命名快照）、链接图层、颜色标签。
- Ai：画板（一份文档多个输出尺寸）、符号（Symbol，改母版全改实例）、外观面板（一个对象多份填充/描边叠加）。
- Lr：**虚拟副本**（同一张原图派生多个参数版本，不复制像素）、收藏夹（跨目录的逻辑集合）。
- PhotoCraft：copy-on-write 256² 稀疏瓦片，撤销便宜、大画布轻；效果图按层状态缓存。

**本工程现状**

扁平数组，z 序 = 数组序。已有 4 条选择命令（`set` / `add` / `toggle` / `clear`），
无对齐/分布、无标签、**无快照**（`history` 只有 undo / redo / clear）。

**评估**

| 能力 | 出处 | 实现模式 | 本工程现状 | 判定 | 成本 | 价值 |
|---|---|---|---|---|---|---|
| 组（含自带 transform / blend） | PS | 子树 + 组缓冲 | 无 | 调整后借鉴（与调整层同批） | L | 高 |
| 虚拟副本 / 变体 | Lr | 原图 + 多组参数（patch） | 只能整份复制工程 | **直接移植** | M | 中高 |
| 画板 / 多尺寸出片 | Ai | 多画布 + 相对布局 | 单画布绝对坐标 | 调整后借鉴（先做安全区） | L | 中（风险高） |
| 符号 / 联动实例 | Ai | 母版 + 实例引用 | 无 | 降级为「图层模板」（不联动） | S | 中 |
| 对齐 / 分布 | PS / Ai | 纯几何 | 无 | **直接移植** | S | 中 |
| 历史快照 | PS / Lr | 命名还原点 | 只有 undo / redo | **直接移植** | S | 中 |
| 图层颜色标签 | PS | 元数据 | `meta` 字段已够用 | 直接移植 | S | 低 |
| 多填充 / 多描边（Appearance） | Ai | 外观栈 | 无 | **不适用** | — | — |

两个要点：

**变体（虚拟副本）比想象中值钱。** 现有工程是「一份文档一套参数」，要做「同一版式的三种配色 /
三种语言」只能复制三个工程，之后改版式要改三遍。变体的做法是 `variant = { baseId, patches[] }`，
打开时 base 与 patch 合成后渲染。这条路与命令层天然契合（patch 就是一串命令 payload），
也能直接在批量导出里展开成三个输出。成本主要在「编辑变体时改动落到哪」——
建议第一版做成**只读派生 + 「固化」按钮**，避免引入「继承 vs 覆盖」的复杂度。

**画板要缓。** Illustrator 的画板能成立，是因为矢量对象有自己的坐标空间与约束；本工程的图层是
绝对像素坐标（`x/y/width/height`），换画布尺寸等于要求重排。没有约束求解器、没有自动布局，
做出来会是「每个尺寸都要手动调一遍」—— 那和复制工程没区别。真正便宜且有价值的一半是
**安全区检查**：给定目标平台（竖版 1080×1920、方版 1080×1080、横版 1920×1080），
检测标题/关键内容是否落在 UI 遮挡区。成本 S，用户立刻能感知。

### 2.4 预设与批量

**对方怎么做**

- PS：**动作**（Action，记录菜单命令序列，可回放、可批处理到文件夹）、Image Processor、脚本。
- Lr：**预设 = 一组参数的命名包**（`.xmp`），可同步设置到多张、可在导入/导出时套用；
  发布服务把「导出」变成可重复的管道。
- PhotoCraft：单一命令注册表（500+），**UI / CLI / JSON 控制通道 / MCP 四个入口共用**；
  `photocraft-cli batch --actions grade.json --in ./raw --out ./graded` 把「动作 + 批量」做成一等公民。

**本工程现状**

- 已有 `custom` 命令（自定义命令）：参数定义 + 默认值 + 占位符替换 + 步骤展开 + 校验。
  **这已经是动作系统，而且比 PS 的更强 —— 它是参数化的，PS 的动作只能录死值。**
- 缺三样：**录制**（只能手写 steps）、**预设包**（导出/导入要确认是否已有）、
  **多工程批量**（`command.batch` 是「多条命令原子执行」，不是「多个工程各导一遍」）。
- 命令注册表已统一 UI 与 AI 工具，**但缺 CLI 与 JSON 控制通道**。

**评估**

| 能力 | 出处 | 实现模式 | 本工程现状 | 判定 | 成本 | 价值 |
|---|---|---|---|---|---|---|
| 动作录制 | PS | 拦截命令 → 生成步骤 | 有步骤引擎，无录制 | 调整后借鉴 | M | 高 |
| 预设包（导出 / 导入 / 分享） | Lr / PS | 参数包文件 | 待确认 | **直接移植** | S | 高 |
| 多工程批量导出 | Lr / PhotoCraft | 队列 + 无头渲染 | 无（只能逐个开） | **直接移植** | M | 高 |
| Headless CLI / JSON 控制通道 | PhotoCraft | 同一注册表的第二入口 | 有 `scripts/render.mjs`（CDP） | 调整后借鉴 | M | 中高 |
| `.atn` 二进制动作兼容 | PS | 私有二进制格式 | — | **不适用** | XL | 低 |

**录制是这里最值得做的一件事**，但有个必须提前想清楚的坑：**运行期 id 的重映射**。
`layer.create` 返回 `ly_xxx`，后面几步的 `layer.update` 引用它；录制时这些 id 是「这一次运行」的，
回放时必须替换成「第 N 步新建的那个」。PS 的动作录制同样有这个问题（它用「当前图层」这种相对引用绕过）。
本工程已有 `substitutePayload` + 占位符机制，正好复用：录制时把「由第 k 步产生的 id」写成
`$step3.id` 这样的占位符，回放时展开。**不做这一步，录出来的动作只能播一次。**

**批量导出不要走「打开工程」这条路。** 正确做法：直接从 IndexedDB 取工程快照 →
`renderToCanvas` / 离屏渲染 → 落文件，全程不碰 `useEditor` 的当前工程状态。理由：
① 切换当前工程会污染撤销栈与「最近打开」；② 用户可能正在编辑另一个工程；③ 无头渲染本来不需要 UI。
要额外处理的是字体就绪与视频素材 seek —— 这两件 `exporters.ts` 里已有先例，复用同一套，别另写。

### 2.5 性能优化

**对方怎么做**

- PhotoCraft：copy-on-write **256² 稀疏瓦片**（只复制被改的瓦片，撤销因此便宜、大画布因此轻）；
  **效果图按层状态缓存**；**两个合成器**（CPU 参照实现 + wgpu GPU 实现）互相对拍；引擎编译到 wasm。
- Lightroom：**预览金字塔**（Minimal / Embedded / Standard / 1:1），编辑期可用 2540px 长边的
  「智能预览」代理原图；**重数据外置**（Lr 15 起把 AI 编辑的重数据放独立的 `.acr` sidecar，
  避免目录膨胀）。
- PS：图层栅格缓存 + 分块重绘 + GPU 合成。

**本工程现状**

`renderScene` 是唯一入口，**每帧全量重绘**：背景 → 逐层 `computeLayerFrame` → 绘制。
没有图层缓存、没有脏矩形、没有预览代理。已有优化只有两处：code 层的 `renderScale`（内部分辨率倍率）
与 `motionBlur` 的子帧采样收敛。离线渲染是多台 headless Edge 分块 + 按序 sink（这是「多进程」）。

**评估**

| 能力 | 出处 | 实现模式 | 本工程现状 | 判定 | 成本 | 价值 |
|---|---|---|---|---|---|---|
| 按图层状态缓存（静态层位图化） | PS / PhotoCraft | cache key = 参数指纹 | 无 | **直接移植** | M | 高 |
| 编辑期降分辨率（代理） | Lr 智能预览 | 低分渲染 + 放大显示 | 只有导出有 scale | 调整后借鉴 | M | 中高 |
| 重数据分离（sidecar） | Lr `.acr` | 元数据与重负载分仓 | 工程 JSON 内嵌源码树 | **直接移植** | S-M | 中高 |
| CPU/GPU 双合成器互检 | PhotoCraft | 两条独立实现对拍 | 两路径共用同一份 canvas2d 代码 | **改做黄金图回归** | M | 中 |
| 256² 瓦片 / 脏矩形 | PhotoCraft / PS | 稀疏瓦片 + 区域失效 | 无 | **不适用**（见下） | — | — |
| GPU 合成 | PS / PhotoCraft | wgpu / WebGL 管线 | canvas2d | **不做**（见下） | XL | 低 |

**瓦片为什么不适用**：瓦片省的是「改了一小块，只重算一小块」。但本工程的画面是**时间的函数** ——
拖一次播放头、改一个关键帧，整幅画面都变。而且 canvas2d 没有 scissor，瓦片化只能靠多个离屏
canvas 拼 `drawImage`，拼合成本比省下的还高。撤销也不痛：immer 的结构共享已经让工程快照很便宜。
**照搬瓦片会把简单问题做复杂。**

**GPU 为什么不做的理由更硬**：离线渲染刻意带 `--disable-gpu`，为的是「软光栅像素跨机器一致」
（既有决策，见 `docs/12-render.md`）。一旦预览走 GPU，预览与离线出片的像素就分叉，
而本工程的底线是「预览即导出」。所以 GPU 只能作为**可选加速**存在，且必须保证「关掉它画面不变」。
真要提速，先做图层缓存，收益/成本比高得多。

**双合成器互检要改成黄金图回归**：PhotoCraft 能做互检，是因为它真的写了两套合成器。
本工程的 `renderScene`（浏览器）与 `scripts/render.mjs`（headless Edge）跑的是**同一份代码**，
对拍只能验证「环境一致」，验证不了「逻辑正确」。等价的低成本做法是把关键帧的出图存成
**黄金图**，CI 里比对像素差；改渲染器时能立刻知道「哪一帧变了」。这是现成资产能直接支撑的
（`render.mjs` 已经能出 PNG 序列）。

## 三、三档分流（汇总）

### 3.1 可直接移植（不动文档模型，或只加字段）

1. **全局色板 / 颜色槽**（Ai Global Swatch）— S-M
2. **预设包导出 / 导入**（Lr 预设）— S
3. **对齐 / 分布**（PS / Ai）— S
4. **历史快照**（PS / Lr）— S
5. **图层标签 / 颜色标记**（PS）— S（`meta` 已够用，低优先）
6. **多工程批量导出队列**（Lr 批量 / PhotoCraft batch）— M
7. **按图层状态缓存**（PhotoCraft effect cache）— M
8. **重数据分离**（Lr `.acr`）— S-M
9. **黄金图回归**（PhotoCraft 互检的等价物）— M

### 3.2 调整后借鉴（模型要翻译，语义要重定义）

1. **组 + 调整层**（PS）— L。组的目的是给调整层提供作用域，必须同批做。
2. **动作录制**（PS Action）— M。难点是运行期 id 重映射，复用现有占位符机制。
3. **变体 / 虚拟副本**（Lr）— M。建议只读派生 + 固化，不做继承覆盖。
4. **固定顺序的调色管线**（Lr）— M。只做 `ctx.filter` 能表达的子集，保证预览 = 导出。
5. **编辑期降分辨率代理**（Lr 智能预览）— M。
6. **Headless CLI / JSON 控制通道**（PhotoCraft）— M。与 `scripts/render.mjs` 合并成一条工具链。
7. **智能对象 → 嵌套工程**（PS）— L。`remotion-component` 已是同构物，可推广。
8. **画板 → 安全区检查**（Ai）— S（完整画板是 L 且风险高）。

### 3.3 不适用（逐条写理由，防止以后反复讨论）

| 能力 | 为什么不做 |
|---|---|
| 画笔引擎 / 笔尖动态 | 本工程的输入是参数与代码，不是笔触；做它等于做第二个产品 |
| 选区（套索 / 魔棒 / 主体选择） | 选区是像素编辑的前置，本工程没有像素编辑 |
| 钢笔 / 路径编辑 | 同上；形状需求用参数化矩形/圆/代码层解决 |
| ICC / CMYK / 16bit / 软打样 | canvas2d 是 8bit sRGB；正确出路是导出时嵌 profile，不是内建 |
| 滤镜库（70+ 种） | 与 code 层重复 —— 要什么效果写几行代码即可，且可复现 |
| `.atn` 二进制动作 | 私有格式反序列化成本极高，收益是「能读旧动作」，本工程没有存量用户 |
| 多填充 / 多描边（Appearance） | 收益低，可用多层叠加近似 |
| 256² 瓦片 / 脏矩形 | 画面是时间函数，不是局部像素编辑；canvas2d 无 scissor |
| GPU 合成 | 会让预览与离线出片像素分叉，违反「预览即导出」 |
| PSD 读写 | 本工程不产出像素文档；要 PSD 应当「当作素材导入」，不是「工程存成 PSD」 |

> 最后一条多说一句：PhotoCraft 花大力气做 PSD 往返，是因为它要替代 Photoshop 的位置；
> Kinelayer 不做 PSD，是因为它的产物是**帧与视频**，不是可再编辑的位图文档。

## 四、推荐落地顺序

排序原则只有一条：**先做「不需要改渲染管线」的，再做「必须一次做对」的。**
前者失败了只是没加成，后者失败了会让预览与导出分叉。

### 批次 1 · 便宜且确定（不动渲染核心）

目标：把「一次性操作」变成「可复用资产」。

1. 全局色板（`palette` + 颜色引用解析 + 命令 + 取色入口）
2. 预设包导出 / 导入（自定义命令 + 色板 + 文本样式打成一个包）
3. 历史快照（`history.snapshot` / `history.restore`）
4. 对齐 / 分布（在 4 条选择命令之上加几何命令）

验收口径：色板改一个槽，所有引用处一次变色；预设包在另一台机器导入后能跑；
快照在 undo 栈被清空后仍可还原。

### 批次 2 · 把入口打通（仍然不动渲染核心）

目标：让「一整套操作」既能录、也能批量跑、也能被脚本驱动。

5. 动作录制（含 id 重映射，复用占位符）
6. 多工程批量导出队列（读工程快照 → 离屏渲染，不切页面）
7. Headless CLI（与 `scripts/render.mjs` 合并，`run <file.kly> --cmd ...`）

验收口径：录一段「建文本层 → 设样式 → 加关键帧 → 导出」的动作，能在另一个工程上回放；
批量导出 5 个工程，当前编辑状态与撤销栈不受影响；CLI 能在 CI 里跑通一次完整导出。

### 批次 3 · 结构性改动（需要专门排期与像素级验收）

目标：补齐「整块一起调」这个能力。

8. 组 + 调整层（组缓冲；兼容 `onlyLayerId` / `overrides` / `transparent`）
9. 固定顺序的 `colorGrade`（限 `ctx.filter` 子集）
10. 变体（只读派生 + 固化）
11. 按图层状态缓存（cache key 设计与失效验证）

验收口径：调整层作用于组内，图层窗口只画单层时不出错；预览与导出在同一帧上像素一致；
缓存失效测试覆盖「改参数 / 改关键帧 / 改色板 / 改 scale」四类。

### 观察（等真实需求，不预先开工）

- 嵌套工程（智能对象的真身）
- 多尺寸画板（先只做安全区检查）
- 图层样式补内阴影 / 外发光
- JSON 控制通道（CLI 有了之后再考虑要不要常驻服务）

## 五、如果只做一件事

**做全局色板。**

理由不是它最酷，是杠杆比最高：一处改动同时改善三件事 —— 模板换色从 20 处变 1 处；
AI 生成只需产出「结构 + 配色槽」而不用逐层写死色值；批量导出多配色版本变成「同一工程 × 多份 palette」。
而且它不动渲染管线（解析放在渲染前），风险最低。

## 六、几条前置预警

1. **颜色字段是散落的**：`TextStyle.color`、`gradient.stops`、`TextStroke.color`、`TextShadow.color`、
   `BackgroundLayer.color`。引入引用后必须**一次全接完** —— 漏一处的结果是「改了色板，某一行字不变」，
   比完全不支持更让人困惑。
2. **缓存失效比缓存命中更难写对**：图层缓存的失败模式是「画面不更新」，比慢更不可接受。
   上缓存前先写好失效测试。
3. **调整层会让「图层窗口只画单层」变含糊**：调整层单独看是什么？建议约定为「不参与单层渲染」
   （`onlyLayerId` 命中调整层时画空），并在界面上说明。
4. **批量导出会遇到字体与视频的异步就绪**：`exporters.ts` 里已有 `await` 字体、`prepareVideos` 的先例，
   批量路径必须复用同一套。
5. **动作录制的 id 重映射是唯一的硬骨头**：先写这一段的测试，再写录制 UI。

## 七、调研方法与边界

- Adobe 三件套：公开文档、官方功能说明、已公开的格式规范（PSD / ICC / XMP）、公开的产品行为描述。
  **未分析任何 Adobe 二进制**（本机也只有 Creative Cloud 客户端，没有应用本体）。
- PhotoCraft：`github.com/storytold/photocraft`（MIT / Apache-2.0），一手材料取其 README 与 `docs/`。
- 本工程现状：以当前提交的源码为准（`renderScene`、`types.ts`、`commands/`、`exporters.ts`）。
- **没有照抄任何代码。** 取的是设计模式；具体实现（尤其 canvas2d 的合成顺序、缓存失效条件）
  都按本工程模型重写。
- 成本标注是**相对量级**（S / M / L / XL = 触点数量与是否动渲染管线），不是工时承诺。

# 11 · 谱面：速度网格与逐字时间

这一章讲两件在 v2.11 之前根本不存在的东西：**`project.tempo`（速度网格）**和
**`project.lyrics`（词级时间）**，以及它们为什么必须是工程级的、为什么不是「音频层的属性」。

配套的示例是第二支片：`示例 · 再改一版（60 秒）`，128 BPM、9 段、21 行歌词、19 层。
它存在的意义不是「又一支样片」，而是把**这套机制的上限**摆出来给人看：
镜头切点落在拍上、卡拉 OK 一字不落地跟着声音、爆点只在强拍上炸。

---

## 1 · 为什么速度网格不能挂在音频层上

最容易想到的做法是让鼓点音源自带 bpm（`tone.bpm` 本来就有），画面去读它。这条路走不通，
原因很具体：

- **一个工程里可能没有鼓。** 只有一条 pad 的时候，画面要贴谁的拍子？
- **半速铺底、三连音是常规手法。** 鼓可以打 64 BPM，片子本身还是 128 —— 这是编曲，不是速度。
- **切镜发生在画面上，但必须落在声音的拍子上。** 两边各算一遍 bpm，改速度时**一定**有一边忘掉，
  然后就会出现「画面切在拍上、鼓差 15ms」。这种偏差在静音预览里看不出来，戴上耳机才发现。

所以速度是**工程级的一份真相**：

```ts
export interface Tempo { bpm: number; offsetMs: number; meter: number }
```

`offsetMs` 是第 0 拍的绝对毫秒位置（可以是负数，表示「从半拍处切进来」）。有了它，
「第几拍」就不再是一个需要拍脑袋对齐的概念，而是一次除法：

```
拍号 = (t - offsetMs) / (60000 / bpm)
```

四件东西共用这一份实现（`src/core/score.ts`，全部是纯函数）：

| 用的人 | 用它做什么 |
| --- | --- |
| 代码层 `api.tempo` | 逐帧查「第几拍 / 拍内相位 / 敲击包络」，画面跟着鼓动 |
| 音频引擎 | 鼓点落在网格上、强拍（小节第一拍）加重 |
| UI | 时间轴上的拍线、检查器里的实时读数 |
| `query.score` | 给 AI 和自检一份「这一毫秒的谱面推导结果」 |

> **敲击包络不来自音频分析。** 鼓本来就打在网格上，所以网格本身就是那一击的准确时刻 ——
> 不需要去听。`hit(tempo, t)` 就是一个半衰期 110ms 的指数衰减，强拍乘 1.35。
> 这是「画面跟着鼓动」的全部秘密，也是它为什么不需要 FFT。

## 2 · 逐字时间：按字符权重切，而不是「排每个字」

本工程的音轨是**合成**的，没有人声可以对齐。所以「每个字什么时候唱」没有客观答案，
只能定义一个不撒谎的口径：

> 一行的区间 `[start, end)` 按各单元的发声权重切分，切出来的单元区间**就是**它的发声区间。

权重规则（`splitLyricUnits` + `unitWeight`）：

- 拉丁按空格成词、CJK 按字；
- 标点黏在**前一个**单元上（它们不发声，不该各自占一段时间），且权重打 0.3 折；
- 单元 i 的高亮区间恰好等于它被分配到的区间，1× 播完即熄灭 —— **绝不领先声音**。

这是「没有音节数据」时唯一能保证「不跑在声音前面」的方案。它不假装精确，它只是不比声音更早。

### 一个真出过的 bug：半分处就报「唱完」

`lineCharProgress` 早期写法在每两个单元之间硬加 1，注释写着「词间空格」：

```ts
if (i < units.length - 1) chars += 1;   // ← 错的
```

对 `hello world` 是对的；对 `先画一条线` 是灾难 —— 中文没有空格，于是五个字的一行
在 54% 处就报「已唱 5/5」，卡拉 OK 整行提前亮起，最后两个字的擦除完全消失。

正确做法是从 `offset` 差算真实跳过的字符数：

```ts
const next = units[i + 1];
if (next) chars += Math.max(0, next.offset - (u.offset + u.text.length));
```

修完 `5000ms` 在 `先画一条线`（4060–5810，五字各占 350ms）上读 **2.686 个字**，
和「53.7% × 5」严格一致。`sample-check` 里的断言从「3 到 6 个字之间」改成了 `2.69 ± 0.06` ——
区间断言放过了这个 bug 很久，这是它的教训：**能用等式就别用区间**。

## 3 · 代码层拿到的东西

```ts
api.tempo = {
  bpm, offsetMs, meter, ms,          // ms = 一拍多少毫秒
  beat, bar, beatPhase, barPhase,    // 连续拍号 / 小节号 / 两个相位
  since,                             // 距上一个整拍多少毫秒
  downbeat,                          // 这一拍是不是强拍
  hit(halfLife?, accent?),           // 敲击包络
  at(i),                             // 第 i 拍是第几毫秒（i 可为小数）
  snap(t, div?),                     // 吸附到 1/div 拍网格
}

api.lyrics = {
  lines, count,
  at(t?), before, after,             // 此刻 / 上一句 / 下一句
  units(line),                       // 逐字时间表
  progress(unit, t?),                // 单个单元 0..1
  chars(line, t?),                   // 已唱几个字（卡拉 OK 要的就是它）
  lineProgress(line, t?),
}
```

写片子时的三条实际用法：

1. **切点用 `api.tempo.at()` 算，不要写裸毫秒。** 改 BPM 时全部跟着走。
2. **爆点只在 `downbeat` 上炸。** 非强拍的爆炸看起来「抢拍」，观众说不出为什么，只觉得廉价。
3. **卡拉 OK 用 `chars()` 裁切，不要用 `lineProgress()`。** 后者是时间比例，前者是字；
   字宽不等，按比例裁会在英文行上明显偏。

## 4 · 子帧运动模糊

`code.motionBlur = { samples, shutter }`：同一帧内按 `shutter` 毫秒的时间窗取 `samples` 个子帧，
叠成一张。

两个坑，都踩过：

- **快门给的是一帧曝光，不是「重影次数」。** 给 `shutter: 110` 而一帧只有 33ms，
  得到的是三次离散重影（长曝光），不是运动模糊。要接近一帧的 `44ms`。
- **叠加必须是增量平均**，不是逐次半透明铺：

  ```ts
  actx.globalAlpha = 1 / (i + 1);
  actx.drawImage(rt.canvas, 0, 0);
  ```

  半透明铺的权重是 front-weighted（后画的更实），结果是「头重脚轻」的拖影；
  增量平均才是等权积分。

代价：绘制次数线性上涨（`samples` 倍），像素数不变。所以它和 `renderScale` 是两条**独立**的杠杆：
前者花绘制次数，后者省像素（平方下降）。片子里只有落版那层叠字用了 `samples: 5`。

## 5 · `u_resolution` 必须是绘图缓冲区的像素尺寸

这条写在这里是因为它花了一整个下午，且症状极其误导。

GLSL 层开了 `renderScale: 0.5` 之后，帧缓冲只有 960×540，而 `gl_FragCoord` 的上限也是 960×540。
如果 `u_resolution` 传的是**图层设计尺寸** 1920×1080，那么 `gl_FragCoord.xy - 0.5*u_resolution`
的中心点落在 `(0,0)` 左上角 —— 画面所有以中心为原点的东西（径向渐变、爆炸、晕影）全部偏到右下。

噪声看不出来（它是无中心的），放射状画面一眼穿帮。修法一行：

```ts
gl.uniform2f(loc, rt.canvas.width, rt.canvas.height);   // 不是 layer.width/height
```

顺带一条纪律：**shader 里用 `gl_FragCoord.xy / u_resolution` 取归一化坐标**，
这样两种 scale 下写法一致。

## 6 · 界面：打拍与歌词

数据层是纯函数，界面是薄的一层，但有两个决定值得记：

### 打拍用墙钟，不用心跳

`performance.now()` 而不是 `setInterval` 的回调时间 —— 后者每跳一次带几毫秒抖动，
而拍点的容差本来就只有十几毫秒。

拟合只做两件事（`fitTaps`）：**中位间隔 → BPM，最后一下 → 相位**。用中位数而不是均值，
是因为打拍的人总会漏一下、早一下，均值会被一次 400ms 的失手整条带偏。

它**不猜**你按的是每几拍：间隔翻倍就是 BPM 减半，界面给 `×2 / ÷2` 让人自己拨。
猜错方向比不猜更糟 —— 用户会以为工具坏了。

还有一条：**暂停时打拍只改 BPM，不碰相位。** 不在播放中时，「第几毫秒按的」没有工程时间的意义，
硬拿它去对相位就是把网格随便挪一下。

### 歌词进出的两种写法

`formatLrc` / `parseLrc` 认两种时间标签：

```
[mm:ss.mmm]              标准 LRC：只有起点，唱到下一句开始
[mm:ss.mmm-mm:ss.mmm]    本工程扩展：带终点
```

扩展形式存在的原因很实在：本工程的歌词**有间隔**（一句唱完留在屏上两秒再出下一句），
这个间隔是编排，不能因为「存成文本」就丢掉。

没带时间戳的行不丢弃，按顺序接在最后一条之后（每句 2400ms 默认）。
于是「把一段词整个粘进来」就能得到一条可播、可再调的歌词轨 —— **先有再准**，
比要求用户手工敲 21 个时间戳现实得多。

## 7 · 自检

`node scripts/score-check.mjs`（23 项）跑的是「界面上按一下，工程里真的变了」：

- 三个输入框读的是工程值；读数与 `query.score` 同源（同一拍、同一偏移）；
- 3750ms 报「小节 03 · 拍 1 · 强拍」，4250ms 报「距上一拍 31ms」；
- 5000ms 报「先画一条线 2/5」（就是第 2 节那个 bug 的回归测试）；
- 每行「起点改成播放头」真的改了起点，并重排；
- LRC 三种行（带区间 / 只有起点 / 没时间戳）导进来各就各位；
- 三下间隔 500ms → BPM ≈ 120；「把播放头当作拍点」把偏移对到相位上；
- 标尺上真的画出 129 条拍线 / 33 条小节线（60s / 128BPM / 4/4）；
- 英文模式下这一块零中文（读数区除外 —— 那里显示的是歌词内容）。

`node scripts/sample-check.mjs`（56 项）里另有两条**谱面数学**的断言：
一拍 468.75ms、4250ms = 第 9.067 拍、3750ms 是强拍且下一强拍 5625ms。

## 8 · 这条路的边界

- **没有真正的音频对齐。** 词级时间是从行区间切出来的，不是从人声里测出来的。
  接了真人声，得先做 forced alignment，再把它当成 `project.lyrics` 的输入 —— 数据结构已经够用了。
- **速度网格是全局恒定的。** 变速（accelerando / 半拍切换）没有建模。真要做，
  `tempo` 得变成一条曲线，那是另一个量级的工作。
- **拍号只影响强拍位置。** 6/8、7/8 这类复合拍能标对强拍，但「3+2+2」的细分没有表达方式。
- **`meter` 上限 16、`bpm` 20–300**：这是给海报型短片定的范围，不是通用 DAW。
